# 第九轮：连续镜头的三种衔接（第 15c-2 步，2026-11-08）

1-06（进屋关门）→ 1-07（手机插入）→ 1-08（开门关门，接 1-06）→ 1-09（拿伞，接 1-08）。都在第八轮整集数据的副本上做，同种子、同输入；B 的提示词和 A 一字不差（改写走缓存）。

```
DRAMA_LIVE=1 uv run --no-sync python scripts/smoke/continuity_abc.py --home <第八轮的数据目录> [--only b,c,cut] [--work <副本>] [--c-file <从 ComfyUI 取回的长镜头>]
```

| 方案 | 做法 | 结果 |
|---|---|---|
| A 尾帧当首帧（产品现在的做法） | 上一条最后一帧当 `h3-i2v` 的首帧 | 1-08 对；1-09 开头门又关上了，在屋里拿黑伞 |
| B 末尾片段续写（PLAN 的方案） | 上一条最后 22 帧（0.92 秒）连声音用官方 `MiniMaxH3AddGuide` 钉在第 0 帧，去掉首帧锚，多要 22 帧、拼接时去掉 | 1-08 对；**1-09 门一直开着，走到门口弯腰拿伞**，最接近剧本「门外拿伞」；脸比 A 稳；切点看不出跳 |
| C 一条 15 秒长镜头 | 1-06 的首帧，一次出 15 秒，剪辑时第 5 秒插 1-07 | **这次不算数**：DeepSeek 改写只写了第一拍（拿到的镜头信息是 1-06 的 5 秒、一句画外音，草稿又因为第一次超时被嵌套了一层），开门、拿伞两拍丢了，后 10 秒人一直站着。不过前 5 秒她真的演出了「进屋、转身、关门」，5 秒的 1-06 没演出来：时间够才演得完 |

- 对比图：`chains-ABC-1fps.jpg`（每秒一帧，从上到下 A、B、C）；`sheet-B-*.jpg`。片子（不进 git）：`../originals/run9-continuity/chain-A|B|C.mp4`、`chain-side-by-side.mp4`（A | B | C 并排，声音是 A 的）。
- 连续镜头一律用整条片子（不按镜头时长裁），否则切点有约 0.3 秒的跳变（第八轮原因 4）。
- 耗时：B 的 1-08（7.29 秒）255 秒、1-09（5.17 秒）190 秒，和 A 差不多。C 的 15 秒片 **804 秒**（5 秒片约 150 秒，按秒算慢约 1.8 倍），第一次被 10 分钟的本地超时掐掉，第二次的脚本进程被 Claude Code 因内存不足回收，片子是从 ComfyUI 的历史记录里取回的。
- 两种方案伞都是黑的：`h3-i2v` 不收参考图，和衔接方式无关（第八轮原因 1、2）。

## 结论

- **B 比 A 好，建议做进产品**：连续镜头用上一条的最后 22 帧（带声音）做引导，取代「最后一帧当首帧」。改动面：视频组件给连续镜头传尾段片段；`h3-i2v` 工作流加一个可选的「尾段引导」槽位（没给时旁路）；take 存时去掉开头 22 帧（代替 0.3 秒裁头）；剪辑按整条片子。
- **C 要重测才能下结论**：提示词得按 15 秒写三拍（改写时告诉模型真实时长和每拍内容，或者手写），本机一条要 13 分钟以上，本地超时得按片长算。
